# 자동 전체 코인 스캐너 및 분류 대시보드 설계

## 목표

PulseRadar Pro가 바이낸스 현물 USDT 전체 종목을 자동으로 스캔하고, 각 종목을 실전 관찰에 유용한 신호 상태로 분류한다. 분류 결과는 모바일 중심 대시보드에서 한눈에 확인할 수 있고, 각 종목은 기존 스냅샷 분석으로 바로 이동한다.

핵심 목표는 다음과 같다.

- 전체 종목을 무작정 깊게 분석하지 않고 1차 빠른 필터와 2차 정밀 분석으로 나눠 API 부하를 제어한다.
- 기존 PRE-SURGE v2, 데이터 신선도 게이트, 스냅샷 분석 로직을 재사용한다.
- 데이터가 오래됐거나 실패한 종목은 반드시 `판정 보류`로 격리한다.
- 이미 크게 오른 종목과 아직 가격 반응 전인 이상징후 종목을 분리한다.
- 초보자도 결과를 이해할 수 있도록 한국어 한줄 요약과 핵심 이유를 제공한다.

## 범위

### 포함

- 바이낸스 현물 USDT 거래 가능 종목 자동 수집
- 다중 시간봉 스캔: `1W → 1D → 4H → 1H → 15m → 5m`
- 1차 빠른 필터
- 2차 정밀 분석
- 신호 상태별 분류
- 보조 섹터 태그
- 모바일 대시보드
- 기존 스냅샷 분석 딥링크
- 데이터 신선도/오류 상태 표시
- 자동 새로고침 및 마지막 스캔 시각
- 회귀 테스트 및 API 계약 테스트

### 제외

- 자동 주문
- 거래소 API 키를 이용한 주문 기능
- 실시간 온체인 전체 네트워크 크롤링
- AI가 임의로 매수/매도 결정을 내리는 기능
- 사용자 자금 규모 기반 포지션 추천

## 사용자 화면 분류

메인 분류는 신호 상태 기준으로 고정한다.

1. `급등 전조 강함`
2. `급등 전조 관찰`
3. `거래량 이상징후`
4. `매수세 유입`
5. `눌림·재축적`
6. `이미 급등함`
7. `약세·이탈`
8. `데이터 부족·판정 보류`

각 종목은 하나의 메인 분류를 가진다. 추가로 다음 보조 태그를 붙일 수 있다.

- AI
- 밈
- RWA
- DeFi
- L1
- L2
- 게임
- 인프라
- 기타

섹터 태그가 불확실한 경우 `기타`로 두고 신호 분류에는 영향을 주지 않는다.

## 아키텍처

### 1. Universe Provider

바이낸스 현물 `exchangeInfo`와 ticker 데이터를 이용해 현재 거래 가능한 USDT 종목 목록을 만든다.

필터 조건:

- 상태가 거래 가능
- quote asset이 USDT
- 레버리지 토큰이나 비정상 심볼은 제외 규칙 적용
- 데이터가 없는 심볼은 스캔 큐에서 제외하고 상태를 기록

출력 예시:

```js
{
  symbol: 'XLMUSDT',
  baseAsset: 'XLM',
  quoteAsset: 'USDT',
  tradable: true
}
```

### 2. Stage 1 Fast Scanner

전체 종목에 대해 저비용 지표만 먼저 계산한다.

주요 입력:

- 24h 가격 변화
- 24h 거래량
- 1h/15m 최근 거래량 가속
- 최근 고점 대비 위치
- 최근 변동성
- 간단한 구조 방향
- 데이터 신선도

목적:

- 정밀 분석할 필요가 없는 종목을 빠르게 제거
- 이미 과도하게 급등한 종목 분리
- 이상 거래량/가격 압축/초기 체결 가속 후보 추출

Stage 1 결과는 `candidateScore`와 `fastReason[]`를 반환한다.

### 3. Stage 2 Deep Scanner

Stage 1 상위 후보와 이상징후 후보만 정밀 분석한다.

입력 시간봉:

- 1W: 대형 추세 방향
- 1D: 중기 구조와 과열 여부
- 4H: 구조 전환/재축적
- 1H: 모멘텀 발생 여부
- 15m: 거래량 및 체결 가속
- 5m: 단기 확인

추가 입력:

- PRE-SURGE v2
- Taker 매수/매도 비율
- OI 변화가 제공 가능한 경우
- 펀딩이 제공 가능한 경우
- 거래량 가속
- 기존 alert state
- 데이터 integrity 상태

OI/펀딩은 현물 전체 종목에 강제로 요구하지 않는다. 해당 데이터가 없는 종목은 `unknown`으로 유지하며 0으로 취급하지 않는다.

### 4. Classification Engine

분류 우선순위는 충돌을 줄이기 위해 고정한다.

1. 데이터 무결성 실패 → `데이터 부족·판정 보류`
2. 최근 단기 급등률/과열 조건 초과 → `이미 급등함`
3. 구조 이탈 + 매도 우위 → `약세·이탈`
4. PRE-SURGE v2 `가능성 높음` → `급등 전조 강함`
5. PRE-SURGE v2 `관찰` → `급등 전조 관찰`
6. 거래량 가속은 강하지만 구조/체결 확인 부족 → `거래량 이상징후`
7. 매수 체결 우위 + 가격 반응 초기 → `매수세 유입`
8. 상위 구조 상승 + 눌림 + 거래량 안정/재증가 → `눌림·재축적`
9. 그 외 → 일반 목록에는 남기되 우선순위를 낮춘다.

분류 결과 구조:

```js
{
  symbol: 'XLMUSDT',
  category: '급등 전조 관찰',
  sector: ['L1'],
  priority: 78,
  dataState: 'live',
  reasons: [
    '1H 거래량이 최근 평균 대비 증가',
    '15m 매수 체결 우위',
    '4H 구조는 아직 상승 유지'
  ],
  tfState: {
    '1w': 'bullish',
    '1d': 'neutral',
    '4h': 'bullish',
    '1h': 'building',
    '15m': 'accelerating',
    '5m': 'confirming'
  },
  updatedAt: 0
}
```

## PRE-SURGE 연계

기존 `PRE-SURGE v2`를 재사용한다.

전체 스캐너에서는 PRE-SURGE를 단독 신호로 쓰지 않고 다음 맥락과 함께 사용한다.

- 상위 시간봉 구조
- 이미 급등했는지 여부
- 단기 거래량 가속
- Taker 흐름
- 데이터 신선도

`가능성 높음`은 다중 조건 동시 충족이 필요하고, 한 가지 지표만 강한 경우는 최대 `관찰` 또는 `거래량 이상징후`로 제한한다.

## 데이터 신선도 정책

다음 상태는 실시간 신호 판정에서 차단한다.

- stale
- failed
- reconnecting
- backfill
- verifying

`delayed`는 실시간 확정 신호로 승격하지 않고 최대 관찰 상태로 제한한다.

UI에서는 다음 정보를 분리한다.

- 데이터 수신 상태
- 마지막 수신 시각
- 캔들 기준시각
- 오류 횟수

## API 및 캐시 전략

전체 종목을 매 요청마다 6개 시간봉으로 전부 깊게 호출하지 않는다.

### 캐시 계층

- 종목 목록: 수 분 단위 캐시
- 24h ticker: 짧은 공용 캐시
- Stage 1 결과: 수십 초~수 분 캐시
- Stage 2 결과: 짧은 TTL + 후보 종목만 갱신

### 동시성

- 제한된 worker pool 사용
- Binance rate limit 고려
- 실패 심볼은 지수 백오프
- 하나의 종목 실패가 전체 스캔을 실패시키지 않도록 격리

## API 계약

새 서버 엔드포인트는 기존 Netlify 함수 패턴을 따른다.

예시:

`/.netlify/functions/coin-scan`

쿼리:

- `mode=summary|deep`
- `category=`
- `sector=`
- `limit=`

응답:

```json
{
  "status": "ok",
  "updatedAt": 0,
  "scanCount": 0,
  "deepScanCount": 0,
  "categories": {},
  "items": []
}
```

응답에는 `partial=true`를 허용해 일부 심볼 실패 시에도 정상 결과를 반환한다.

## 쉬운 요약

요약은 신호를 과장하지 않는다.

예시:

> 큰 흐름은 상승 쪽이지만 아직 급등이 확인된 상태는 아닙니다. 1시간 거래량과 단기 매수 체결이 늘고 있어 관찰 대상입니다. 데이터는 정상입니다.

반드시 포함할 요소:

- 큰 구조 방향
- 현재 모멘텀 상태
- 왜 해당 분류인지
- 데이터 상태

## 섹터 태깅

초기 버전은 정적 매핑 파일을 사용한다.

장점:

- 빠르고 안정적
- 외부 API 장애와 무관
- 테스트 가능

향후 별도 단계에서 공개 데이터 소스로 자동 갱신할 수 있지만, 초기 구현에서는 신호 엔진과 섹터 메타데이터를 분리한다.

## 실패 및 예외 처리

- Binance 일부 요청 실패: 해당 심볼만 `판정 보류`
- 전체 upstream 실패: 기존 캐시가 있으면 `delayed`로 제공
- 캐시도 없으면 명확한 오류 상태 표시
- JSON 파싱 실패/스키마 불일치: 해당 공급자 결과 무시
- 0 또는 누락 값을 실제 수치로 오인하지 않음

## 성능 목표

초기 목표:

- Stage 1은 전체 종목을 짧은 시간 안에 완료
- Stage 2는 후보 종목만 수행
- 모바일 첫 화면은 전체 결과를 기다리지 않고 캐시된 마지막 결과부터 표시
- 사용자 스크롤 없이 상위 이상징후 목록 확인 가능

정확한 SLA는 실제 Netlify/Binance 호출량을 측정한 뒤 조정한다.
